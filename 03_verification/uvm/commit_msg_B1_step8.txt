B1: refuse duration_cycles=0 and prove the refusal left nothing behind

Three behaviours, kept apart so one cannot cover for another: the driver refuses
the illegal item by name, the refusal leaves no trace on the pin, and the driver
can still run the next window.  A zero is injected by hand because the item's
default is 600 and the constraint keeps it in [100:8000], so the value can only
come from a directed test; the comment in the rejection branch said "the item's
own default", which stopped being true when the default changed.

Sequence, all with no TU driven:
  1. a legal 100-cycle window, so the pin is known to be in guard afterwards and
     a later req=1 cannot be attributed to the driver never having started;
  2. an item with duration_cycles=0 whose other fields are legal and stall often
     (light_mod=3, deep_period=8, deep_len=16) - if it were applied the pin
     would go low within a few cycles, so a pin that stays high is evidence;
  3. a deliberate 20-cycle gap, then a second legal window with a different
     pattern (light 3/5, deep 24/10) whose waveform is easy to tell apart.

Judged on four things rather than on "the error was reported":
  - exactly one ITS_GRANT_DUR and no other UVM_ERROR id, via the case's exact id
    set, so a second report or a different id fails;
  - the rejected item returns with no cycle of execution (end == begin) and its
    own begin/end records both carry duration 0;
  - the driver recorded two profiles, not three: a rejected item must not appear
    as an applied profile;
  - the guard stretch between the rejection and the next window is all req=1 and
    at least 15 edges long, and the second window's first edge, executed count,
    waveform and completion time all match the contract.
