## 四、两处必须记住的更正

**D1 对比口径**：`GAPS.csv` 有两套口径——`global_gap=True`（任何实例都没执行过）和任意实例级。按 global 口径：D1 语句 143 行 / 分支 132 行，UVM 148 / 128，交集 137 / 126，仅 UVM 缺 11 / 2。结论是"量级相当、各有长短"。中途我曾用 954（任意实例级）去比，得出"UVM 缺口被完全包含、UVM 更深"——那是错的。

**tail 那 11 行**：不是 UVM 的激励缺口。实测 32×32 + 600 拍输出关断后仍 0 命中；D1 是靠 `03_verification/tb/unified_its_hread_raw_capture_tb.sv:186` 的 `force dut.u_unified_p4_kernel.in_req = 1'b0;` 打进去的。`in_req` 是 kernel 子模块内部信号，公共接口无法在保持 valid/ready 合法的前提下把它按低，所以这是白盒 force 类用例的覆盖点，不属于协议层回归。

## 五、已知限制

- 数值正确性依赖项目向量集（369 case），UVM 层未独立实现变换模型
- 随机化的对象是用例抽取/顺序/间隔，不是描述符本身的随机生成
- 两个 agent 按管脚组拆分（激励 / 反压），**不是两路 DUT 通道并发**
- 复位只测了"处理途中拉低 rst_n"一种时序，未覆盖复位抖动或多拍复位
- 覆盖率是 DUT 单模块口径（991 条语句），未与 D1 的 UCDB 跨套件合并
- 分支缺口有一次账目对不齐：`vcover` 摘要报 144 miss，明细 CSV 145 行，差 1 行原因未查明
- 条件/表达式的块内缺项合计（30 / 63）与汇总（44 / 66）也有同类粒度差，未对齐
- L616 / L651 的表达式覆盖率与同行语句命中数矛盾，判不清是内联还是报表问题
- 第 5、7、8 类缺口标"未能证明可达"，证明需要形式化论证或 force 注入
- end 归属那一类（H）可达但本轮没构造，需要"两槽占满 + 队列填到 2 + 冗余 end"的时序
