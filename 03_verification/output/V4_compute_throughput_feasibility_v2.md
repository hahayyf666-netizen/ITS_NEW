> 日期：2026-08-08
> 基线：V3.2 冻结 RTL（its_core_500=04241edc, async_fifo=08254a2a）
> 目的：核对第 4 项"一拍计算四个点"，量化当前吞吐，以 VTM 快速反变换为唯一算法来源评估可行性。

## ⚠ 关键发现（影响全部后续工作）

### 发现 1：当前实现用 T·x，VTM 快速逆变换用 Tᵀ·x

对 canonical DCT2-4 逐点验证：

| 输入 | T·x（当前 ref_model/RTL） | Tᵀ·x（VTM 逆变换） |
|------|:--:|:--:|
| x=[1,0,0,0] | [64,83,64,36] | [64,64,64,64] |
| x=[0,1,0,0] | [64,36,-64,-83] | [83,36,-36,-83] |
| x=[0,0,1,0] | [64,-36,-64,83] | [64,-64,-64,64] |
| x=[0,0,0,1] | [64,-83,64,-36] | [36,-83,83,-36] |

**全部 one-hot 输入均不同。**

- `ref_model.inverse_transform_1d` 计算 `y = T·x`（VVC 前向变换矩阵直接乘）
- VTM `fastInverseDCT2_B*` 计算 `y = Tᵀ·x`（数学正确逆变换）
- 对非对称变换（DCT2、DST7），两者**逐点不同**
- DCT8 对称（Tᵀ=T），两者一致

**验证规模**：13 个变换 × 1110-1170 输入（one-hot + 随机 + 极值 + 稀疏 + 溢出），VTM 快速模型与 Tᵀ 参考**100% 一致**。

### 发现 2：canonical DST7/DCT8 32×32 与 VTM 不一致

| 矩阵 | canonical JSON vs VTM RomTr |
|------|:--:|
| DCT2 全部尺寸 | ✅ 一致 |
| DST7 4/8/16 | ✅ 一致 |
| DCT8 4/8/16 | ✅ 一致 |
| **DST7/DCT8 32×32** | ❌ **496/1024 项不同** |

当前 canonical JSON 的 DST7/DCT8 32×32 可能提取有误（V1 列分解）。

### 发现 3：问题陈述自相矛盾

> 名称："**反变换**模块（ITS）" → 逆变换 = Tᵀ
> 正文："变换模块作为将**时域信号转化为频域信号**" → 前向 = T

**当前实现用 T·x（符合正文"时域→频域"）。若评审按 VTM 逆变换（Tᵀ）验证，当前实现不匹配。这是必须由赛方澄清的根本歧义。**

**影响**：VTM 快速原型（Tᵀ）与当前 golden（T）**逐点不一致**，原型验证受阻。后续原型必须先用 T 或 Tᵀ 的明确决定。

## 一、当前真实性能（解析模型，已验证与实测吻合）

1D 变换引擎状态机（its_transform_engine.v）：

| 阶段 | 周期 | 说明 |
|------|:--:|------|
| S_LOAD | N | 加载输入 |
| S_PREFETCH | 4N | 预取 4 行系数 |
| S_COMPUTE | N | 4 MAC 并行累加 |
| S_OUTPUT | N | 输出 |
| 主循环 | N/4 组 | 每组 = PREFETCH(4N) + COMPUTE(N) = 5N |

**首组 4 结果 @ 6N 周期；组间隔 5N 周期；1D 总周期 = 2N + 5N²/4**

| N | 首组@ | 组间隔 | 1D 吞吐 | 2D 吞吐 |
|:--:|:--:|:--:|:--:|:--:|
| 4 | 24 | — | 0.143 | 0.052 |
| 8 | 48 | 40 | 0.083 | 0.040 |
| 16 | 96 | 80 | 0.045 | 0.022 |
| 32 | 192 | 160 | 0.024 | 0.012 |
| 64 | 384 | 320 | **0.012** | **0.006** |

模型验证：4×4 解析 ~306 周期 vs 协议测试实测 310 周期，吻合。

### 概念严格区分

| 概念 | 当前实现 |
|------|:--:|
| 4 次乘加/拍 | ✅ 4 MAC |
| 4 个正在累计的输出点 | ✅ 4 累加器 |
| 4 个计算完成的最终系数/拍 | ❌ 每 N 拍完成 4 个 |
| 输出接口传输 4 系数/拍 | ✅ V3.1 零气泡（FIFO 排空） |

## 三、达到 4 最终系数/拍的乘法器下界

### 3.1 直接矩阵乘法（方案 A）

每个最终系数需要 N 次乘加。**4 结果/拍 = 4N 乘法器/拍 + 4 棵 N 输入归约加法树。**

| N | 乘法器 | 系数带宽 | 加法树深度 |
|:--:|:--:|:--:|:--:|
| 4 | 16 | 256 bit/拍 | 2 级 |
| 8 | 32 | 512 bit/拍 | 3 级 |
| 16 | 64 | 1024 bit/拍 | 4 级 |
| 32 | 128 | 2048 bit/拍 | 5 级 |
| 64 | **256** | **4096 bit/拍** | 6 级 |

**修正**：5 DSP → 256 DSP 是 **51.2×**（非"面积约 4×"）。加法树必须流水化后才能尝试 500MHz（6 级 64 输入归约树单拍组合逻辑不可行）。

**N=64 系数带宽**：256 系数/拍 × 16bit = **4096 bit/拍**。RAMB36E2 单端口最大 72bit（或 36bit 双口）。4096/72 ≈ **57 个 RAMB36E2 读端口**，或系数复制 57 份。当前 ROM 用 12 RAMB36 + 5 RAMB18。**BRAM 增长约 4-5×（仅系数存储），远超当前 14.5 tile。**

**500MHz 可行性**：**必须综合原型验证，不得预先断言确定可行。** 256 个 DSP 的布线拥塞 + 6 级归约树流水化 + 57 宽 ROM 读，均有高风险。

### 3.2 快速变换（方案 B，VTM 蝶形）

| N | DCT2 乘法器下界（4结果/拍） | 说明 |
|:--:|:--:|:--|
| 64 | ~1368×(4/64) ≈ **86** | 蝶形总乘法摊到 16 拍/向量 |
| 32 | ~344×(4/32) ≈ **43** | |

**但**：DST7/DCT8 N=32 需 ~620 乘法（N=8 无蝶形 = 64 直接）。峰值在蝶形最深层（O 节）需 N/2 输出 × N/2 乘法并行。

**乘法器下界远低于方案 A，但代价是复杂蝶形控制和深度流水。不可假设"24-48 足够"——DCT2-64 需 ~86，DST7/DCT8-32 需 ~78 持续。**

### 3.3 端到端吞吐（单引擎 vs 双引擎）

**单引擎复用两遍**（当前架构模式）：
- 行变换 + 列变换串行
- 若行/列各达到 4 结果/拍，端到端平均仍被串行化折半
- 严格 4 结果/拍端到端需要**独立行/列双引擎 + ping-pong 转置缓存**（避免转置等待）

## 四、三种架构方案（修正版）

### 方案 A：4N 并行乘法 + 4 棵 N 输入归约加法树

| 项 | 评估 |
|----|------|
| 乘法器 | **4N 个**（N=64 需 256 = **51.2× 当前 5 DSP**） |
| 加法树 | 4 棵 N 输入归约树，必须流水化（6 级@N=64） |
| 系数带宽 | 4N×16bit/拍 = 4096 bit/拍 → ~57 RAMB36 读端口 |
| 500MHz | **必须综合验证**（布线拥塞 + 树流水化高风险） |
| 真正 4 结果/拍 | ✅ 数学确定 |
| 面积/功耗 | DSP 功耗 ~2.5W（现 0.012W），**总功耗约 4-5×**，面积大幅增长 |

### 方案 B：VTM 快速变换（蝶形/部分分解）

| 项 | 评估 |
|----|------|
| 乘法器 | DCT2-64 ~86，DST7/DCT8-32 ~78 持续（非 24-48） |
| 系数 | VTM 整数矩阵（与当前 ROM 同源，但需 Tᵀ 约定） |
| 500MHz | 蝶形级简单，可行；但深度流水控制复杂 |
| **真正 4 结果/拍** | 理论可行（流水蝶形稳态） |
| **最大风险** | **T·x vs Tᵀ·x 约定未定**；DCT8/DST7 部分无蝶形（N=8 直接） |
| 验证 | 与 canonical golden 的 Tᵀ 一致性需重新建立 |

### 方案 C：多 bank ROM + 交错流水

| 项 | 评估 |
|----|------|
| 本质 | 数学上仍是 4N MAC/拍，**退化为方案 A** |
| 改进 | ROM 带宽解决，乘法器数不变 |
| 结论 | 不能独立达标 |

## 五、题面歧义评估

| 解释 | 含义 | 当前实现 |
|------|------|:--:|
| 宽松 | 每拍并行执行 4 个点的一次乘加 | ✅ 4 MAC/拍 |
| 严格 | 每拍完成 4 个新的最终结果 | ❌ 每 N 拍完成 4 个 |

**不得假定宽松解释成立。** 若评委严格解释，当前计算核心不满足第 4 项。

**叠加发现 1（T·x vs Tᵀ·x）**：即使达到 4 结果/拍，还必须决定用 T 还是 Tᵀ。当前 golden 用 T·x，VTM 参考用 Tᵀ·x。

## 六、原型可行性结论（决策门之前）

**原型被 T·x vs Tᵀ·x 约定阻塞。** VTM 快速原型（Tᵀ·x）与当前 canonical golden（T·x）逐点不一致，无法通过"与 golden 逐点一致"验收。

### 决策门

必须先解决两个问题，才能进入原型：

1. **T 还是 Tᵀ**：赛方应澄清第 4 项的逆变换约定。若用 Tᵀ，则当前 V1-V3 golden 和 RTL 需整体修正（影响 1539 回归和 ROM）；若用 T，则 VTM 快速原型需改造成 T 版本（失去 VTM 参考依据）。
2. **DST7/DCT8 32×32**：canonical 矩阵需与 VTM 对齐。

### 只有两个最困难原型通过后才制定 V4 RTL 替换方案

- `_v4_prototype/dct2_64/`（DCT2 N=64 一维流水）
- `_v4_prototype/mts_32/`（DST7 或 DCT8 N=32 一维流水）

验收：流水填满后每拍 4 最终系数、逐点匹配 golden、2.000ns OOC 闭合、连续多向量无气泡、支持背压。

**本阶段未修改任何 RTL。**
